### Image 1: assembly view (`out/assembly_view.png`, `.svg`, `.puml`)

- **Intent:** show every part of the cubesat, how the parts assemble and which parts can be swapped or tuned, so a reader sees what a configuration is made of and which of its choices are categorical (a part is swapped) and which continuous (a part's parameter is tuned).
- **Selection:** package `CubesatTradeSpaceV2`, part def `Cubesat`, its part usages with their types (usages that share a type, `panelPlus` and `panelMinus`, share one box and are named in it); each abstract part def with its concrete alternatives (by specialization); the enum def that selects each alternative; attributes stated with `default` (`panelSpan`, `batteryCapacity`, `Kp`, `Kd`), each placed once, in the part def whose usage binds it (`:>> span = Cubesat::panelSpan` puts `panelSpan` in `SolarPanel`; the redefined `span` and `capacity` are the same variables and are not shown again); levels and ranges read with `Model.eval`. Excluded: calculated attributes, environment, scenario, calcs, requirements, gain-box instances other than their ranges.
- **Encoding:** top to bottom; `Cubesat` on top, its parts in one rank, alternatives below their abstract part (hollow triangle = specialization; composition diamond = part of); the same tag in a part box for every configuration variable and nowhere else, orange `swap` for a categorical variable (`WheelClass`, `TrackerGrade`, on the abstract part) and blue `tune` for a continuous one (`panelSpan`, `batteryCapacity`, `Kp`, `Kd`); a legend below the graph (crossing no line) names the tags and gives the levels and ranges read from the model.
- **Shows:** all parts and their assembly; the six configuration variables, once each, in two kinds; the alternatives of the two swapped parts; the numeric ranges and category levels. **Does not show:** each alternative's attribute values (mass, torque, momentum, accuracy, power); the environment; any calculation; requirements; which gain box (baseline or aggressive) applies to a given configuration beyond the two range lines.
- **Line routing:** the composition lines are polyline segments from the `Cubesat` box to the top of each part box and the specialization lines run from each abstract box to its alternatives; none crosses a box (checked on the rendered image at 700 px). `ortho` routing was tried first and rejected: it stacked the edges onto one bus above the parts.

### Image 2: behavioural view (`out/behavioural_view.png`, `.svg`, `.puml`)

- **Intent:** show, per functional subsystem, which requirements the model states, which of the ten traded metrics each requirement reads, and which metrics are traded with no requirement on them, and where each metric comes from (the analysis def or the measurement of the slew), so a reader can follow the chain from the model to the metrics.
- **Selection:** the three subsystems and the ten metrics (with their order and grouping) from `CaseSpec` in `examples/adcs/case.py` (controls, power and energy, mass); every `requirement def` of the package with its `satisfy` and `verify` elements (read from `SatisfyRequirementUsage` and the `verification def` objectives); the `analysis def` `SlewExperiment`; `SlewMeasurement`. A requirement-metric line is drawn only where the model gives evidence (all derived from the model's JSON, none typed): thick = the requirement and the metric read the same measured quantity (`baselineMeasurement.X`) or invoke the same calc directly; dashed = they share a calc only further upstream, or the model's prose (a `doc`) names the metric in the requirement's text. The label on the line is the shared calc, quantity or `prose`. The metric-to-model-identifier table (`METRIC_ELEMENT`) is the one thing typed in the script, checked against the model on every run (the analysis must return it, or the measurement must name it).
- **Encoding:** left to right; orange boxes requirement defs (with the satisfy and verify elements as lines; "none in the model" when absent), green metric boxes have at least one requirement relation, dashed white metric boxes are traded with none, a requirement that no traded metric reads says so in bold; grey arrows run from the analysis def or the measurement into the metrics; subsystems are the three packages.
- **Measurement and fielded systems:** here the verification and analysis take their measurements by simulation (the evaluation of a configuration into attributes); a fielded system's own data would take the simulation's place in `SlewMeasurement` and enter the same way.
- **The analyst's reading, not model elements:** (1) which subsystem a requirement sits in (CaseSpec groups metrics, not requirements): derived from the subsystems of the metrics it relates to, and for `MomentumRequirement`, which relates to none, set by `ANALYST_SUBSYSTEM` (controls); (2) the strength labels thick and dashed (the model states no "constrains" relation between a requirement and a metric at all; thick and dashed grade the evidence); (3) the `SlewBandRequirement` to slew time line rests on one sentence of prose ("it qualifies the slew-time attribute"), not on an element; (4) the line from `SlewMeasurement` to slew time rests on the prose of the experiment section (the settling time and the slew time are measured and pass into the output row unchanged; `SlewMeasurement` has no slew-time attribute).
- **Shows:** 3 of 10 metrics read with a requirement on the same quantity (settling time, eclipse reserve, depth of discharge), 2 only through a shared upstream calc (power margin, energy balance), 1 by prose (slew time), 4 with none (pointing error, total mass, control effort, peak slew power); `MomentumRequirement` reads no traded metric (peak momentum is measured but is not one of the ten); the mass subsystem has no requirement; every requirement is satisfied only by `cubesatBaseline`. **Does not show:** the formulas or the thresholds; the measured inputs other than by the grey arrows; the calc-to-calc dependency graph; the assembly.

### Gap list for image 2: what makes each metric's relation explicit

| Metric (subsystem) | Relation in the model today | Element that would make it explicit |
|---|---|---|

| eclipse reserve (power and energy) | `DepthOfDischargeRequirement` bounds `EclipseDemand` by `maxDepthOfDischarge * capacity`, which is the reserve being non-negative; the two share the calc `EclipseDemand`, but the model does not say they are the same statement | restate the requirement over `EclipseReserve(c, e) >= 0`, or add a `verify` objective naming the reserve |

requirements are `satisfy`-ed by `cubesatBaseline` only, not by the configurations of the trade space.

## Verdict

Two diagrams are worth a slot, and both come from one small projection script, not from a built-in view:

1. **Configuration** (slot 1): `out/slot1_configuration.puml`. Legible at 700 px; marginal at 375 px.
2. **Configuration to attributes** (slot 2): `out/slot2_attributes.puml`. Legible at 700 px only as a
   structural overview (labels are small); not legible at 375 px.

No built-in pipeline gives either. The OpenSysML runtime and sysml-toolkit both run and exit 0, but
their package-level views are unusable at column width and neither draws requirements, calcs or the
analysis as a dependency picture. Slot 1 is the stronger candidate. Slot 2 is honest but busy (27
boxes); if the paper has room for one figure only, take slot 1.

## Recipe 1: configuration (slot 1)

- **Question:** what is a configuration of the cubesat: what is chosen and from what.
- **Subject and selection:** package `CubesatTradeSpaceV2`, part def `Cubesat`. Included: its part
  usages with their types; abstract part defs and their concrete alternatives (by specialization); the
  enum def that selects each alternative (literals listed); attributes stated with `default`
  (the design variables: `panelSpan`, `batteryCapacity`, `Kp`, `Kd`); numeric ranges read with
  `Model.eval` from `designRanges`, `baselineGains`, `aggressiveGains`. Excluded: calculated attributes,
  environment, scenario, calcs, requirements.
- **Encoding:** filled box is the part def under consideration; composition diamond with the usage
  name; hollow triangle is specialization (an alternative); notes give the selecting enumeration and
  the ranges. The word "(variable)" marks defaulted attributes.
- **Shows:** the two categorical variables as the abstract wheel and tracker with three alternatives each;
  the four continuous variables with ranges; the fixed parts.
- **Does not show:** the attribute tables of each alternative (mass, torque, momentum, accuracy, power);
  which composed parts are fixed versus chosen other than by the absence of alternatives (the
  note and "(variable)" tags carry it); the environment; the formulas.
- **Files:** `out/slot1_configuration.puml`, `.svg`, `.png`, `_700.png`, `_375.png`.
  At 700 px all text reads. At 375 px the labels are readable but small, the stereotypes are not.
- **Known wrinkle:** `panelSpan` and `batteryCapacity` appear on `Cubesat` and again as the redefined
  `span` and `capacity` on `SolarPanel` and `Battery` (marked "(variable)" there, because they are `default` in the part def).
  The `(variable)` on those two is a consequence of the rule, not a statement that panels carry their own variable; a caption or a selection rule (variables of the root only) would settle it.

## Recipe 2: configuration to attributes (slot 2)

- **Question:** which calculations take a configuration to the attributes, and which requirements the same configuration is held to.
- **Selection:** calc defs, requirement defs, analysis defs and verification defs directly under the
  package, with `Cubesat`; edges from invocations found in the model JSON (`to_api_json`), taking the
  nearest top-level container as the caller. Pruned to what is reachable from `Cubesat`, the analysis
  and the requirement defs (this drops the closed-form slew-time calcs and the two verification
  defs, which nothing reaches). Constraint defs are omitted (parameter): they restate the accounting for the solver.
- **Encoding:** blue box the configuration type, green box the analysis `SlewExperiment`, orange boxes
  requirement defs, white boxes calc defs; solid arrow is "invokes"; dashed arrow `<<satisfy>>` goes to
  the named configuration the model asserts it for.
- **Shows:** the seam: the analysis's eight returned calculations, the shared sub-calcs (generation,
  eclipse demand, inertia), the accounting calcs the configuration evaluates itself, and which requirement reads which calc.
- **Does not show:** that two of the ten attributes (settling time and slew time, with control effort)
  are measured from the simulation and enter as inputs; which edge is which of the ten attributes (the
  analysis edges carry no label; the ten are not nodes); the constants and formulas; input and output
  types; the Python simulator outside the model; that four of the five requirements take measured
  inputs. The requirements appear nearly disconnected from the calcs because they read measured inputs.
- **Files:** `out/slot2_attributes.puml`, `.svg`, `.png`, `_700.png`, `_375.png`. At 700 px the box
  labels read but the stereotypes are tiny; at 375 px nothing reads. It wants a full-width or landscape slot.
- **Honest caveat:** this is a dependency overview, not a data flow of the ten attributes. Calling
  it the "analysis" figure would overstate it.

## Limits

- The projection depends on `to_api_json` (marked experimental by opensysml, an `ExperimentalFeatureWarning`) and on element-id spelling (`::` in queries, `__` in JSON); a runtime upgrade can break it, which a pinned test would reveal.
- Light and dark were not rendered: PlantUML output has a white background by default; a dark-theme variant was not tried.
- Reading the PNGs was done by me at the stated widths; a human judgment of legibility is still due.
- I did not write a PlantUML writer for the 0.12.1 `render_view` typed output, and I did not run the toolkit with `--show-inherited` or `--color`, which might make the toolkit's Cubesat tree show more.
- `sysml-toolkit` 0.12.0 `viz` accepts `--view` of seven kinds; the model has no state, action, sequence or connector content, so those views were not meaningful tests.
- 375 px PNGs are resampled from the full render, not drawn at that size.

## Cost to adopt

- One script (`project.py`, about 200 lines; presentation settings are constants at its top), run with `uv run python`. It uses only opensysml, which is already locked.
- Committed: the generated `.puml` text and an SVG (or PNG) for the paper; the model is the source, the text is a build product.
- A test could pin the generated PlantUML text byte-for-byte (stable across three runs here) and could assert
  that every node name occurs in the model and that specific edges exist (e.g. `PowerRequirement --> ...`).
  Such a test needs the opensysml runtime (downloaded to `~/.opensysml` on first connect) but not PlantUML or Java.
- Rendering to SVG needs `plantuml` and Java (system tools, not uv packages). CI would either skip
  the render and compare text only, or install them in the workflow; the committed image is the one the paper uses.
- A model change in `model_v2/cubesat.sysml` means regenerating and recommitting the pair; the text diff shows what changed.
